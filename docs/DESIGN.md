# Fieldnote — Design & Architecture

## Problem

Field inspectors work on sites with poor or no network coverage. Most apps treat offline as an error state — a spinner, a "no connection" banner, a dead screen. Fieldnote treats the device as the source of truth: the phone's local database is the real data, and the server is something it _catches up with_ later, not something it depends on to function.

## Architecture

```
Screens (src/app/**)
   │  calls
   ▼
Repositories (src/repositories/*)
   │  calls
   ▼
Drizzle (src/db/schema.ts, src/db/client.ts)
   │
   ▼
SQLite (fieldnote.db, on-device)
                                          ↓ (Phase 3)
                                   Sync engine → Supabase
```

Every screen goes through a repository; every repository goes through Drizzle; nothing talks to SQLite directly except Drizzle itself. This is enforced as a project rule, not just a convention — see decision D-004.

## Decision log

### D-001: Device-generated UUIDs instead of server auto-increment

- **Date:** 2026-08-25
- **Decision:** every table's `id` is a UUID v4, created on the phone at the moment of insert (`src/lib/id.ts`, via `expo-crypto`).
- **Why:** an offline inspector must be able to create a record — an inspection, a project — with a permanent ID _right now_, with no server reachable. A server-issued auto-increment ID (1, 2, 3…) requires asking a server for the next number, which doesn't exist offline.
- **Trade-off:** UUIDs are 36 characters versus a few digits — larger keys, marginally slower indexes and a bigger database file at scale.
- **Rejected:** auto-increment (impossible offline); server-reserved ID blocks, where the phone pre-fetches a batch of IDs while online to hand out later (workable, but needs connectivity to refill and adds a whole subsystem for a problem UUIDs solve for free).

### D-002: Soft delete only — a `deletedAt` timestamp, never a real `DELETE`

- **Date:** 2026-08-25
- **Decision:** "deleting" a row sets `deletedAt` to the current time and leaves the row in place. Every read filters `isNull(table.deletedAt)`. Nothing in the app runs a real SQL `DELETE` against an entity table.
- **Why:** a hard delete offline can't be synced. If the row is simply gone, Phase 3's sync engine has no way to tell the server "this record used to exist and the user removed it" — the server never learns, and depending on sync direction the row could even reappear. A soft delete is itself the message that gets synced.
- **Trade-off:** every table grows forever (deleted rows are never purged in Phase 1); every read needs the `deletedAt IS NULL` filter, which is one more thing to remember and forget.
- **Rejected:** hard delete with a separate `tombstones` table recording what was deleted — functionally similar to soft delete but needs a second table and a join, for no real benefit at this scale.

### D-003: Timestamps as epoch milliseconds (INTEGER), never ISO strings

- **Date:** 2026-08-25
- **Decision:** every `*_at` column is `integer`, storing `Date.now()` — milliseconds since 1 January 1970.
- **Why:** comparing and sorting plain integers is trivial and unambiguous. ISO strings (`"2026-08-30T12:00:00Z"`) invite subtle bugs: string-sorting `"2026-8-9"` against `"2026-08-10"` gives the wrong order, and timezone-suffixed strings vary in format depending on where they were generated.
- **Trade-off:** a raw integer isn't human-readable in a database viewer — `src/lib/time.ts#formatTimestamp()` exists purely to convert one for display, and is never used for storage or comparison.
- **Rejected:** ISO 8601 strings (sorting/timezone footguns above); `Date` objects (SQLite has no native date type — Drizzle would still serialize it to one of the other two options anyway).

### D-004: The repository layer is the only code allowed to import Drizzle

- **Date:** 2026-08-25
- **Decision:** `src/repositories/*.ts` are the only files that import `db`, `schema`, or any `drizzle-orm` query builder. Screens (`src/app/**`) and components (`src/components/**`) call repository functions and never see a query.
- **Why:** Phase 3 needs every mutation to also write an outbox row. If ten screens wrote to the database directly, the same discipline would need to be re-applied ten times, and any screen missed becomes a change that silently never syncs — the worst kind of bug, because nothing _looks_ wrong. With one layer responsible, there is exactly one place to get it right.
- **Trade-off:** an extra function call and file for even the simplest read; can feel like ceremony for a one-off query.
- **Rejected:** letting screens query Drizzle directly with a "remember to add outbox writes" convention — relies on memory across dozens of call sites instead of a door that can't be skipped.

### D-005: `outbox` does not carry the common `createdAt/updatedAt/deletedAt/syncStatus` columns

- **Date:** 2026-08-25
- **Decision:** unlike every entity table, `outbox` has its own distinct column set (Section 4.2.6 of the Phase 1 plan) rather than sharing `commonColumns()`.
- **Why:** an outbox row is a to-do note, not a syncable entity in its own right — it is never itself updated, soft-deleted, or given a sync status. Giving it those columns would be four columns that are always meaningless.
- **Trade-off:** one table shaped differently from the other five, which is one more thing to remember when reading `schema.ts`.
- **Rejected:** reusing `commonColumns()` for consistency's sake — consistency that documents a lie (that outbox rows can be "updated" or "deleted") is worse than an documented exception.

### D-006: `.sql` migrations imported at build time via `babel-plugin-inline-import`, not read at runtime

- **Date:** 2026-08-25
- **Decision:** `drizzle-kit generate` (driver `expo`) produces raw `.sql` files plus a `drizzle/migrations.js` loader that imports them directly (`import m0000 from './0000_init.sql'`). `metro.config.js` adds `sql` to Metro's `sourceExts`; `babel.config.js` adds the `inline-import` plugin so each `.sql` file's _raw text_ is inlined as a JS string at bundle time.
- **Why:** a phone app can't `fs.readFile()` a `.sql` file at runtime the way a Node script could — everything the app needs must be bundled in. Verified directly: without the Babel plugin, Metro's default JS transformer tries to parse raw SQL as JavaScript and fails immediately with a syntax error (`Missing semicolon`, pointing at the `CREATE TABLE` keyword) — this is exactly the failure Section 3.4.3 of the Phase 1 plan warned this integration is fragile enough to hit.
- **Trade-off:** two config files (`babel.config.js`, `metro.config.js`) whose only job is this wiring, and both must exist together — either alone still fails to bundle.
- **Rejected:** hand-writing migration SQL as JS template strings directly (works, but throws away `drizzle-kit generate`'s automatic diffing between schema versions — see Section 2.7 on why migrations matter at all).

### D-007: A second migration, `projects.notes`, to prove upgrades don't destroy data

- **Date:** 2026-08-25
- **Decision:** added a nullable `notes` column to `projects` and ran `npm run db:generate`, producing `drizzle/0001_add_project_notes.sql` (`ALTER TABLE projects ADD notes text;`) alongside the existing `0000_init.sql`.
- **Why this exists as its own decision, not just "a column got added":** Section 3.4.4 of the Phase 1 plan is explicit that one migration proves nothing — an empty database "migrates" fine no matter what. Only a _second_ migration, applied to a database that already has real rows in it, proves the upgrade path itself doesn't wipe or corrupt existing data. The column chosen (`projects.notes`) is deliberately nullable, so every row seeded under `0000_init` — before this column existed — still satisfies the new schema with no backfill step required.
- **Trade-off / honest limitation:** this decision and the migration file exist; what it's meant to _prove_ — that installing an app containing `0001` over a device that already ran `0000` and has real data leaves that data intact — has not yet been verified on an actual device in this session (no Android Studio or physical phone available in this environment). See `docs/TEST-RESULTS-PHASE-1.md`, TC-10, which is intentionally still marked **Not yet run**, not upgraded to a pass on the strength of the migration file existing alone.
- **Rejected:** picking a column with no real use (a throwaway `debugField`) purely to exercise the migration machinery — `notes` was chosen instead because it's a real, small, genuinely useful addition (projects had no notes field; inspections already did), so the migration also does something worth keeping rather than being pure ceremony.

### D-008: A reverse proxy in front of Metro's web dev server, to make `expo-sqlite` web actually loadable — dev tooling only, not the shipped app

- **Date:** 2026-08-27
- **Decision:** `npm run web` now goes through `scripts/dev-web-coi-proxy.js` (`npm run web:coi`, wired as the default web launch config) — a small Node script that runs `expo start --web` as a child process and sits a reverse proxy in front of it, adding `Cross-Origin-Opener-Policy: same-origin` and `Cross-Origin-Embedder-Policy: require-corp` to every response that passes through.
- **Why this is needed at all:** `expo-sqlite`'s web backend runs SQLite compiled to WebAssembly inside a Web Worker, and that requires `SharedArrayBuffer` to share memory between the page and the worker. Browsers only grant a working `SharedArrayBuffer` to a page that is "cross-origin isolated," which requires those two headers on the actual HTML document response — not just on the JS bundle.
- **Why not just add the headers from `metro.config.js`'s `server.enhanceMiddleware` (the obvious first attempt):** tried it first, and verified directly why it fails: `enhanceMiddleware` only wraps Metro's own middleware, and the root `/` document for `expo start --web` is generated by a different part of Expo's dev server that runs _before_ that hook and fully handles the response itself. Headers set inside `enhanceMiddleware` reliably land on JS bundle requests (confirmed via a debug log) but never once reached the actual page — `self.crossOriginIsolated` stayed `false` no matter what. A reverse proxy sits at the HTTP layer _outside_ Expo's server entirely, so it stamps every response regardless of which internal handler produced it.
- **What this does and doesn't fix, being honest about it:** the proxy genuinely solves the `SharedArrayBuffer` problem — confirmed directly (`crossOriginIsolated: true`, `typeof SharedArrayBuffer === "function"`) after switching to it. It does not, by itself, make `expo-sqlite` web fully work in every browser — see D-009 and D-010, which go further into what was found past this point.
- **Trade-off:** a new dev dependency (`http-proxy`), a new script, and one more moving part in the dev workflow (`web:coi` runs two processes — Metro plus the proxy — instead of one) — all of it strictly for a target platform (web) that was never this project's actual deliverable.

### D-009: Patched `expo-sqlite` web (via `patch-package`) to fall back to an in-memory VFS when a browser lacks `createSyncAccessHandle`

- **Date:** 2026-08-27
- **Decision:** `patches/expo-sqlite+57.0.1.patch` changes `node_modules/expo-sqlite/web/worker.ts` so that, before creating its persistent storage backend (`AccessHandlePoolVFS`), it feature-detects `FileSystemFileHandle.prototype.createSyncAccessHandle` — an OPFS API not every browser implements. If present, behavior is unchanged (real, persistent, OPFS-backed storage). If absent, it registers a plain in-memory `MemoryVFS` (already bundled with `expo-sqlite`, used elsewhere for `:memory:` databases) as the persistent VFS instead, logging a clear warning that data won't survive a reload in that browser. `npm run postinstall` runs `patch-package` automatically, so the patch reapplies after any fresh `npm install` without manual steps.
- **Why patch a third-party package at all, when D-006 rejected something similar for the SQL-migration loader:** that rejection was about avoiding a _worse_ solution to a problem that already had a clean one (Babel plugin). This is different: `expo-sqlite` genuinely has no built-in escape hatch for a browser missing this one specific API — without a patch, every database in a browser like that fails outright rather than degrading. `patch-package` keeps the change small, reviewable in a plain diff, and automatically reapplied — not a silent, unmaintainable fork.
- **What this fixes, precisely:** browsers that support real multi-threaded `SharedArrayBuffer`/`Atomics` sharing (the mechanism D-008's proxy unlocks) but happen not to implement the newer, narrower OPFS sync-access-handle API yet.
- **What this does NOT fix — see D-010:** this patch turned out not to be the reason the sandboxed environment this project was built in still couldn't run the database on web. That's a separate, deeper issue.
- **Trade-off:** one more moving part (a patch file + postinstall step) that needs revisiting on every `expo-sqlite` upgrade — `patch-package` will fail loudly (not silently) if the patch no longer applies cleanly, which is the point.
- **Rejected:** leaving the eager, unconditional `AccessHandlePoolVFS` initialization as-is and just documenting the limitation — rejected because the fix here is small, safe (identical behavior in browsers that support the API), and turns a hard crash into a graceful, clearly-logged degradation for the browsers it does help.

### D-010: The web preview's real, unfixable-from-here blocker is a browser threading gap, not OPFS — diagnosed directly, not guessed

- **Date:** 2026-08-27
- **Decision:** no code change — this is a documented finding, reached by instrumenting `expo-sqlite`'s worker with temporary diagnostic messages (added, verified, then fully removed — never shipped) to see past the generic `"Sync operation timeout"` error. The instrumentation proved: the worker receives the `open` message, successfully initializes wa-sqlite, and successfully returns a result (`handleMessageImpl resolved`) — but the main thread's `Atomics.load()` spin-loop (in `drizzle-orm`'s and `expo-sqlite`'s synchronous worker-call mechanism, `invokeWorkerSync`) never observes the worker's `Atomics.store()` that should signal completion, and eventually gives up.
- **Why this means D-009's OPFS patch, while real and worth keeping, wasn't the actual blocker here:** the timeout happens on _every_ database call, not specifically ones touching persistent storage — and the diagnostic trace shows the worker's actual SQLite work completing fine. The only step that fails is two threads observing the same `SharedArrayBuffer` as truly shared memory, which is a JavaScript-engine-level threading capability, not something any `expo-sqlite`, Drizzle, or Fieldnote code controls.
- **Why this can't be worked around from here:** `drizzle-orm/expo-sqlite`'s entire query execution path (`prepareSync`/`executeSync` — confirmed by reading `session.cjs`) is built on this synchronous worker call. There is no async alternative wired into the Drizzle driver to fall back to — the mismatch would need to be fixed in the browser engine itself, not in application code.
- **Why this very likely won't affect a real desktop browser:** genuine cross-thread `SharedArrayBuffer` sharing is old, foundational, near-universally-correct functionality in any standard Chromium or Firefox build — unlike OPFS's `createSyncAccessHandle`, which is newer and genuinely inconsistent across browsers. Its failure here is far more likely to be specific to this project's sandboxed/embedded preview browser than a general web-platform limitation. `npm run web:coi` has a real chance of working end-to-end in an ordinary up-to-date desktop Chrome or Edge — untested here, since only the sandboxed browser was available while building this.
- **What this changes about D-008's claim:** D-008 originally attributed the remaining gap to the OPFS API specifically. That was a real, verified finding (D-009 fixes it), but not, in the end, the operative cause of the failure in this environment — recorded here rather than quietly edited away, so the actual debugging path stays visible.

### D-013: Repositories fall back to an in-memory mock store when the real database can't open — dev/preview tooling only

- **Date:** 2026-08-27
- **Decision:** `src/db/client.ts` now opens the database inside a `try/catch` instead of letting a failure crash at module load. On failure it sets `dbInitError` and leaves `db` as `null`; `isDbAvailable()`/`requireDb()` are the two functions everything else uses to ask about that state. Every repository (`projects.ts`, `inspections.ts`, `templates.ts`, `outbox.ts`, `seed.ts`) checks `isDbAvailable()` first and, when false, delegates to `src/db/mockStore.ts` — a small, self-contained, in-memory implementation of the same read/create/edit/delete operations, seeded with a handful of realistic rows. `src/app/_layout.tsx` renders the exact same navigation and screens either way, adding only a persistent banner in the fallback case.
- **Why this exists at all:** D-010 established that this project's sandboxed web preview cannot open a real database — a genuine, confirmed browser limitation, not an app bug. Without something to fall back to, that specific environment could not render a single real screen, which defeats the entire purpose of using it to sanity-check UI changes as the app grows. Every other target (Android, iOS, a normal browser) is completely unaffected — `dbInitError` stays `null` there, and every line of this behaves exactly as it did before this decision.
- **Why the fallback lives in the repository layer and not as a separate hand-built mock screen:** a separate mockup screen would need to be manually kept in sync with every real screen change, forever, and would silently go stale — exactly the failure mode a project this document-driven is trying to avoid. Falling back at the data layer means the _real_ screens, routes, and components render — unmodified, automatically staying current as the app grows — with only where their data comes from changing.
- **Why this doesn't call it a day and just fake everything:** mutations that would need a real device to make sense (`updateProject`, `softDeleteProject` — Phase 1 doesn't even expose these in the UI) throw a clear "not available in preview mode" error rather than silently pretending to work. The Settings screen's outbox count reports `0` in this mode rather than a fabricated number, because there genuinely is no outbox — mock mutations don't queue anything to sync, since there's nothing real to sync.
- **Trade-off:** a second, parallel (if much smaller) implementation of each repository's data operations to keep in mind — `src/db/mockStore.ts` is deliberately kept tiny and clearly commented as non-authoritative so this doesn't become "which one is right" confusion later. Also: this can mask a real bug that only manifests against actual SQLite — the banner exists specifically so nobody mistakes preview-mode behavior for a verified real-database result.
- **Rejected:** hand-building a separate, static "preview" screen tree using mock data directly in JSX (goes stale as the app grows — see above); swallowing the error and showing a permanent loading spinner (technically honest, but defeats the entire reason this was requested — being able to see screens as they're built); disabling the whole idea and only ever testing on-device (correct for final verification, but leaves zero way to sanity-check UI changes in this sandboxed environment specifically).

### D-014: Ran the Phase 1 test cases through the web preview where possible — what it could and couldn't actually verify

- **Date:** 2026-08-28
- **Decision:** no code change to the app's data layer. Section 6.2's test cases were exercised directly, live, in the running `npm run web:coi` preview, and `docs/TEST-RESULTS-PHASE-1.md` was updated with the real observed outcome of each — not a guess about what the code "should" do. Two real, previously-undocumented findings came out of this pass and are recorded below.
- **Finding 1 — `Alert.alert`'s confirm dialog never fires on React Native Web, at all, on any browser.** Clicking "Delete Inspection" produced no dialog and no state change. Root-caused, not assumed: `window.confirm` was monkey-patched to a call counter before clicking — it recorded zero calls — and `node_modules/react-native-web/src/exports/Alert/index.js` was read directly, showing `class Alert { static alert() {} }` — a literal empty stub. This is unrelated to D-010's `SharedArrayBuffer` gap; it would be true in a normal desktop Chrome too. It only affects the web preview — the same `Alert.alert(...)` call in `settings.tsx`/`inspections/[id].tsx` is fully functional on real Android/iOS, which do implement it natively. Nothing was changed to work around this — polyfilling `Alert.alert` with `window.confirm` on web would be extra code whose only job is making a dev-only preview tool's delete button clickable; the real behavior on the platforms that matter is already correct.
- **Finding 2 — `mockStore.ts`'s seed templates didn't match `seed.ts`'s real seed templates.** The mock store (D-013) seeded templates named "Roof Inspection" / "Equipment Check" — Phase 2's real template names — while Phase 1's actual `seed.ts` seeds three differently-named placeholder templates. Caught by literally reading the New Inspection screen's template picker in the running preview and noticing the names didn't match what `docs/TEST-RESULTS-PHASE-1.md` and `seed.ts` already documented. Fixed: `mockStore.ts`'s `seedTemplates()` now uses the same two names (truncated to two, matching the mock's smaller fixture set) as `seed.ts`'s real `TEMPLATE_DEFS`. This was a preview-mode-only cosmetic mismatch — it could never have caused a real bug on device, since `mockStore.ts` is never reached there — but a test pass that finds nothing usually means it wasn't looking hard enough, so it's recorded rather than fixed silently.
- **What this does and doesn't change about Phase 1's Definition of Done:** it does not close the physical-device gap — the plan's actual test cases (6.2.1–6.2.5) are written around real on-device SQLite persistence, real airplane-mode/force-quit behavior, and a real 500-row scroll, none of which the mock store or a browser can stand in for. What it does do: several test cases that are really about **UI/navigation/validation correctness**, not persistence, now have a genuine, live-verified result instead of "Not yet run" — because those specific behaviors (tab navigation, filtering, empty states, dark-mode contrast, title-required validation, long-title layout, Fast Refresh) run through the exact same screens and components regardless of which data layer is underneath them.
- **Rejected:** treating "the web preview ran without crashing" as informal evidence Phase 1 is device-ready — rejected, because the mock store's very existence (D-013) means a clean web run proves nothing about real SQLite, real persistence across restart, or real migrations, which are precisely the parts of the plan's Definition of Done still unverified.

## Phase 2

### D-015: Templates stay inline objects in one TypeScript file, not separate hand-authored JSON files

- **Date:** 2026-09-06 (implemented outside this project's plan-mode sessions — see the note below)
- **Decision:** the two real Phase 2 templates (Roof Inspection, Equipment Check) are plain JS objects in `src/db/templateDefs.ts`, each `JSON.stringify()`'d into the `templates.schema_json` column at seed time. This is different from the Day 1 plan drafted earlier in this project's history (`src/db/templates/*.json` files plus a `src/types/template.ts` discriminated union) — that work was never built; this shape was instead implemented directly against GitHub, with GitHub Copilot, in a session outside this project's usual plan-mode-first workflow. Recorded here after the fact rather than silently treated as if it had always been the plan, per this project's own documentation protocol.
- **Why this is still an acceptable shape:** the plan's actual requirement (Section 1.4.2) is that templates are hand-authored, not built through an in-app editor — a plain `.ts` object satisfies that exactly as well as a `.json` file does. The runtime shape stored in the database (`schema_json`, parsed at read time) is identical either way; only the _authoring_ location changed.
- **What was lost by skipping the typed-union approach:** no compile-time exhaustiveness checking on field types — `FormRenderer.tsx`'s field-type `switch` and `src/lib/validation.ts` both type template fields as `any` and only fail at runtime (a typo'd `type` renders as "Unsupported field type," not a build error). This is real, working tech debt, not a defect that blocks Phase 2 — but it's the concrete cost of the shortcut, named rather than left implicit.
- **Rejected:** rewriting the already-working templates into the originally-planned typed-JSON-file shape purely for consistency with an earlier, abandoned plan — rejected because it would touch working code for no behavioral gain, days after the fact. If a third template (Phase 2's own Day 7 engine-proof test) or a Phase 3 need justifies the stronger typing later, that's the moment to revisit this, not now.

### D-016: Fixed a Phase 2 merge that didn't actually pass `npm run typecheck`/`npm run lint` — and one genuinely missing feature found while fixing it

- **Date:** 2026-09-13
- **Context:** the Phase 2 feature set (dynamic form rendering, photo/GPS/signature capture, autosave, validation) was built and merged into `phase-1` on GitHub, outside this project's sessions, with its own commit message claiming "Phase 2 implementation complete." Pulling that work into this session and actually running the project's own required gates (CLAUDE.md: "must pass with zero errors before any commit") showed it did not meet that bar — `npm install` itself failed outright.
- **Finding 1 — `expo-file-system@~15.0.1` (and its four sibling native packages) were declared with version numbers that don't exist for Expo SDK 57.** `npm install` failed with `ETARGET` before any code even ran. Fixed by running `npx expo install` for the four Expo-managed packages (resolves the SDK-57-correct versions automatically) and pinning `react-native-signature-canvas` to a version whose semver range is satisfiable (the declared `^0.5.0` cannot match any `5.x` release — a 0.x caret range only floats within `0.x`).
- **Finding 2 — `expo-file-system`'s API changed shape entirely since whatever version the original code was written against.** The code called the old function-style API (`FileSystem.documentDirectory`, `.getInfoAsync()`, `.writeAsStringAsync()`, `.makeDirectoryAsync()`, `.copyAsync()`) — none of which exist on the installed v57 package, which ships a new class-based `File`/`Directory`/`Paths` API instead (the old shape now lives only under the separate `expo-file-system/legacy` import). Rewrote `src/lib/media.ts` and `FormRenderer.tsx`'s signature-save path against the real, current API (confirmed by reading the installed package's own `.d.ts` files, not assumed) rather than importing the legacy shim — per this project's own `AGENTS.md`: "Expo HAS CHANGED... read the exact versioned docs before writing any code."
- **Finding 3 — a real feature gap, not just a build error: `visibleIf` was checked during validation but never applied when rendering.** `src/lib/validation.ts` correctly skips a hidden field's validation, but nothing in `FormRenderer.tsx` ever filtered `section.fields` by the same rule — so a conditionally-hidden field (e.g. the Roof template's "Photograph the damage," meant to appear only when `roof_condition` is `fair`/`poor`) rendered unconditionally, on every inspection, regardless of the actual field's current value. Confirmed live in the web preview before and after the fix, not assumed from reading the code alone: the photo field showed with no condition set, and correctly appeared/disappeared as `roof_condition` was changed once `isFieldVisible()` (mirroring validation.ts's exact check) was added and used to `.filter()` the rendered field list. This is precisely what TC-12–15 in `docs/TEST-RESULTS-PHASE-2.md` were written to test — it would have failed the moment anyone actually tried those steps.
- **Also fixed:** `mockStore.ts`'s preview-mode templates had drifted from `seed.ts`'s real ones a second time — not just the names (already fixed once, D-014) but the schema shape itself (`{ fields: [] }` instead of real `sections`), which crashed `FormRenderer.tsx`'s `schema.sections.map(...)` the instant an inspection was opened in the web preview. Fixed by extracting the two real templates into `src/db/templateDefs.ts`, a single file both `seed.ts` and `mockStore.ts` import — there is no second copy left to drift. Also: a `react-hooks/immutability` lint error from mutating a `useMemo`-held `Map` (the autosave timer registry) — moved to `useRef`, which is what mutable per-render state that must survive re-renders without triggering them is actually for.
- **Verification:** `npm install`, `npm run typecheck`, and `npm run lint` all pass clean (zero errors, zero warnings). Live-verified in the running web preview: a template's real fields render (not a crash), conditional visibility now genuinely shows/hides the photo field as `roof_condition` changes, and tapping "Add photo" in a browser with no real camera degrades to the existing placeholder-attachment fallback without crashing — none of this was assumed from the type checker alone.
- **What this does not fix:** none of this touches the actual device-dependent claims already marked "NOT VERIFIED" in `docs/TEST-RESULTS-PHASE-2.md` (real photo compression size, real GPS accuracy, the signature canvas's real touch/draw behavior) — those still need a physical device, exactly as that file already said. Fixing the build and one real rendering bug is not the same claim as device verification, and isn't being presented as one.

## Phase 3

### D-017: Server-side schema mirrors the local one, keyed by `owner_id`; `server_updated_at` — not any client timestamp — is the only clock conflict resolution may ever trust

- **Date:** 2026-09-13
- **Decision:** `supabase/migrations/20260913000001_init_schema.sql` creates `projects`, `inspections`, `answers`, `attachments` (mirroring `src/db/schema.ts` column-for-column) plus `templates` (shared, no owner) and `sync_idempotency_keys` (Day 2). Every owned table adds two columns no local table has: `owner_id uuid references auth.users(id)`, and `server_updated_at timestamptz`, stamped by a trigger — `new.server_updated_at = now()` — on every insert and update, using **Postgres's own clock**, never a value the client sends.
- **Why a trigger and not "just read `now()` in the client's request handler":** there is no separate request-handler layer yet (Day 1 talks to Postgres directly through Supabase's auto-generated REST API, not a custom server) — a trigger is the one place guaranteed to run on every write regardless of which path reaches the table, including ones added later (Day 2's push logic, or any future direct edit from the Supabase dashboard).
- **Why this is the one rule most likely for a future change to accidentally break:** comparing two rows' plain `updated_at` (the device-supplied one, already in the local schema) looks completely reasonable — it's right there, same name, same shape. It is also exactly what silently loses data the moment one phone's clock is wrong (plan Section 2.8). Recorded here, and in `CLAUDE.md`'s new "Sync rules," specifically because it's the mistake that wouldn't look like a mistake.
- **`templates` has no `owner_id`:** templates are hand-authored reference data (Phase 2's "no template-editor UI" rule), not something any individual user creates — RLS grants `select` to any authenticated user and no client gets `insert`/`update`/`delete` at all.
- **`local_uri` is mirrored on `attachments` but is nullable and non-authoritative:** it's a path on one specific phone's filesystem — meaningless to any other device or to the server. `remote_url` (Day 6) is the column every other device actually reads.
- **Rejected:** epoch-millisecond `bigint` for `server_updated_at`, to stay literally identical to every other timestamp in the schema — rejected because it would need this column re-derived from the client-visible `updated_at`'s existing convention, which defeats the entire point of it being a value the client never supplies. A native `timestamptz`, set only by a trigger, makes "the client cannot influence this" structurally true instead of a rule someone has to remember.

### D-018: RLS looked correct and wasn't enough — two real bugs found only by actually trying to break it, not by reading the policy SQL

- **Date:** 2026-09-13
- **Decision:** no policy changed. What changed: this project's Supabase instance needed an explicit `grant` (see `supabase/migrations/20260913000002_grants.sql`) before RLS could even be evaluated at all.
- **Finding 1 — "permission denied for table projects," not an RLS rejection.** The first attempt to insert a row as a real authenticated user failed outright. RLS policies decide _which rows_ a role may touch; Postgres's ordinary `GRANT` system decides whether the role may touch the _table_ at all, and this project's instance did not have the `authenticated` role auto-granted on newly created tables. Fixed with `grant select, insert, update, delete on ... to authenticated` (and `select` only on `templates`). This is a genuinely different failure mode from a bad policy, and the two are easy to conflate from the error message alone if you don't actually read it.
- **Finding 2 — confirmed the policies work, by breaking them, per the plan's own instruction (Section 2.3): "Test it by trying to break it."** Wrote a throwaway script (`@supabase/supabase-js`, the same public anon key the app ships with, two freshly-created accounts) that: (1) had user A insert a project, (2) had user A read it back, (3) had user B try to read the exact same row by id, (4) had user B try to insert a row claiming `owner_id` = user A. Real, observed results: A sees the row (1 row), B sees nothing (0 rows, no error — RLS filters silently, exactly as designed), and B's forged insert is rejected outright ("new row violates row-level security policy"). All three matched what the policy SQL claimed it would do — but claimed and confirmed are different things, and only the second one is in this file because it's the only one that's true.
- **Why a script instead of testing this through the app's UI:** Day 1's screens don't call Supabase for data yet (that's Day 2's push/pull work) — there was no UI path to even attempt this through. A small script talking directly to the same backend, with the same public key, tests the actual thing that matters (does the database itself enforce this) independent of whether any particular screen has been wired up yet.
- **Rejected:** trusting the policy SQL's own `using (auth.uid() = owner_id)` clauses as sufficient evidence on their own — rejected, because Finding 1 is proof that a schema can look completely correct and still reject every request for an entirely unrelated reason. Reading code is not the same as running it; this project has hit that exact gap enough times now (D-014, D-016) that it's not treated as a one-off anymore.

### D-019: Push is a Postgres RPC function, not a hand-written HTTP endpoint — and the outbox row's own id is the idempotency key

- **Date:** 2026-09-13
- **Decision:** `supabase/migrations/20260913000003_sync_push.sql` adds one function, `sync_push(idempotency_key, entity_type, entity_id, operation, payload)`, called from the client as `supabase.rpc("sync_push", {...})` (`src/lib/syncApi.ts`). It checks `sync_idempotency_keys` first; if the key's been seen, it returns the recorded response unchanged (`{ duplicate: true }`) instead of touching any table. Otherwise it applies the insert/update/delete to the right table (`project` / `inspection` / `answer` — see below) and records the response, all inside the one implicit transaction a single Postgres function call already gets for free.
- **Why a database function instead of the plan's literal `POST /sync/push` over a hand-rolled server:** this project has no server process of its own — Supabase's managed Postgres + auto-generated API _is_ the entire backend. Getting "check the idempotency key, apply the change, record the key" to happen atomically would otherwise mean either (a) three separate client round-trips with an obvious race between them, or (b) standing up and deploying a Supabase Edge Function (a whole separate Deno runtime, its own auth wiring, its own deploy step) to wrap what is, underneath, a single database operation. A `plpgsql` function gets the atomicity for free and ships with the same `supabase db push` that already deploys the schema.
- **Why the outbox row's own `id` is the idempotency key, not a separately generated value:** it already exists (Phase 1, D-001 — a device-generated UUID, created the moment the row was queued), it already uniquely names "this one specific pending change," and it never needs to be generated, stored, or kept in sync with anything else. Inventing a second identifier for the exact same purpose the first one already serves would be complexity with no corresponding benefit.
- **Why only `project`/`inspection`/`answer`, not `attachment`, this week:** an attachment _row_ with no uploaded file behind it (`remote_url` stays null until Day 6) would sync a lie — a record other devices would see and think "the photo is available," when it isn't anywhere but the original phone's disk. `sync_push` explicitly rejects `entity_type = 'attachment'` with a clear error rather than silently accepting and doing something misleading with it.
- **A real bug found while wiring this up, not a hypothetical:** `src/repositories/answers.ts`'s `saveAnswer` built its **update**-path outbox payload with keys `{ text, number, json }` (the function's own parameter names) while its **insert**-path payload correctly used the real column names `{ valueText, valueNumber, valueJson }` — a Phase 2 inconsistency that never mattered until something actually needed to read that JSON by column name. `sync_push`'s `answer` branch does exactly that. Fixed by making the update path build the same `{ valueText, valueNumber, valueJson, updatedAt }` shape the insert path and the real schema both already use.
- **Live-verified, not assumed** (a throwaway script, `@supabase/supabase-js`, same as D-018's RLS check): the exact same push request sent twice produced one project row and a `duplicate: true` second response; a partial update payload (`{ name, updatedAt }` only) changed `name` and left every other column — `address`, `notes`, coordinates — untouched; an inspection insert referencing a real, already-pushed project succeeded, and the identical insert against a made-up `projectId` was rejected with Postgres error `23503` (foreign key violation); an answer's partial update changed `valueText` while `valueNumber` stayed `null`, not overwritten to something wrong.
- **What Day 2 does not yet cover, on purpose:** no retry or backoff on failure (a failed row just stays in the outbox, tried again next manual drain — Day 3 adds scheduled backoff with jitter), no automatic trigger on reconnect (Day 3), and the actual **client-side** drain loop (`src/lib/syncEngine.ts`, the Settings screen's "Sync Now" button) is typecheck/lint-verified and calls this exact, proven RPC correctly by inspection — but has not been exercised end-to-end on a device. This web preview's real SQLite (and therefore its real `outbox` table) never opens at all (D-010) — there is structurally no real outbox here to drain, the same device-only gap every earlier phase has hit. The server side is proven; the on-device wiring to it needs a phone, exactly like every other "Not yet run" row in this project's test results.
- **Rejected:** having `sync_push` trust an `ownerId`/`owner_id` field inside the payload itself — rejected outright, always deriving it from `auth.uid()` server-side instead, so a compromised or buggy client can never write a row it claims belongs to a different account (this is the same property D-018's RLS test already proved for direct table writes; the RPC deliberately doesn't reopen that door).

### D-020: Dead-lettering is a `nextAttemptAt` far enough in the future to be unambiguous, not a new column — and why `attempts` alone isn't a safe way to detect it

- **Date:** 2026-09-14
- **Decision:** `src/lib/backoff.ts` implements the plan's own formula exactly — `min(1000 * 2^attempts, 300_000)` doubling delay, then scaled to 50–100% of that value for jitter. `src/lib/syncEngine.ts#pushOne` computes a fresh delay from each row's current `attempts` on every retryable failure and writes it to the existing `outbox.nextAttemptAt` column (no schema or migration change needed — this column already existed, just unused past Day 2's "always due immediately" default). Once `attempts` would reach `MAX_ATTEMPTS` (8) — or immediately, for a failure `src/lib/syncApi.ts#isRetryable` already classifies as permanent — `nextAttemptAt` is set to roughly a year out instead of a computed delay: not a real deadline, just a value guaranteed to be past `MAX_DELAY_MS` from now, which is all `listPendingOutboxEntries`'s `nextAttemptAt <= now()` filter needs to naturally stop selecting that row on every future automatic drain.
- **Why this needed its own decision entry — a real bug caught before it shipped:** the first version of this classified a dead-lettered row by checking `attempts >= MAX_ATTEMPTS` wherever the UI or the retry action needed to know "is this one dead?" (`getOutboxSummary`, `retryDeadLetters`). That's wrong for a **permanent** failure: `isRetryable` can decide a row is dead-lettered on its very first attempt (`attempts = 1`), long before it would ever reach `MAX_ATTEMPTS` on its own. Caught by re-reading `pushOne`'s own two failure branches side by side, not by running into it live — both branches were writing the same `nextAttemptAt` sentinel, but only one of them was also making `attempts` big enough for the other functions' check to agree. Fixed by giving both `getOutboxSummary` and `retryDeadLetters` one shared function, `isDeadLettered(entry)`, that asks the same question `pushOne` effectively already answered when it wrote the row: is `nextAttemptAt` further out than any real backoff delay could ever schedule? `attempts` plays no part in that check anymore.
- **Why a sentinel timestamp and not a dedicated `deadLettered` boolean column:** a new column would need a Drizzle schema change and a fresh migration for something the existing `nextAttemptAt` column can already express unambiguously — "not due for a very long time" already _means_ "not going to be tried automatically," without inventing a second, parallel way to say the same thing that could theoretically disagree with the first.
- **The "syncing" status is real, not cosmetic:** `pushOne` sets an entity's `syncStatus` to `"syncing"` immediately before the network call and only moves it to `"synced"`/`"pending"`/`"failed"` once the result is known — visiting that state matters because it's what lets the Day 3 status UI (`SyncStatusDot`) show a row genuinely mid-flight, not just jump from "waiting" to "done" with an invisible gap most users would read as the app doing nothing.
- **Connectivity triggers (`src/lib/syncTriggers.ts`) fire on the OFF→ON transition only, not every network event.** `NetInfo` also reports Wi-Fi ↔ cellular handoffs while staying connected the whole time — treating every one of those as "reconnected" would trigger pointless drains throughout a normal commute. A module-level `wasConnected` flag is the one piece of state needed to tell a real reconnection apart from a lateral handoff.
- **A `syncInFlight` guard prevents overlapping drains** when the foreground trigger and the connectivity trigger fire close together (opening the app the instant Wi-Fi reconnects, for example) — `drainOutbox`'s own "one row at a time, in order" guarantee (D-019) would mean nothing if two separate drains could run concurrently against the same outbox.
- **Live-verified, not assumed:** the backoff formula itself was run directly (not through the app) for attempts 0 through 11 — delays visibly grow (711ms → ~193s across that range in one real run), plainly show jitter (consecutive high-attempt delays vary rather than repeating the same capped number), and never exceed `MAX_DELAY_MS`. The dead-letter classification fix was verified by re-deriving both failure branches' behavior by hand against the corrected `isDeadLettered` check, not just re-reading the original (already-once-wrong) code. What remains genuinely unverified on a device, for the same D-010 reason as Day 2: whether `NetInfo`'s reconnect event and `AppState`'s foreground event actually fire and actually trigger a real drain against a real outbox — the listeners are typecheck/lint-clean and match documented library APIs, but nothing in this environment can produce a real "airplane mode off" event to observe them firing.
- **Rejected:** resetting `attempts` to 0 automatically after some elapsed time (a row that's been failing for an hour "forgiving itself") — rejected because it would silently un-dead-letter a row nobody asked to retry, contradicting the entire point of a dead letter being something a human decided to act on (`retryDeadLetters`, the manual "Retry Failed" button) rather than something that quietly resolves itself.

### D-021: Pull is plain PostgREST reads, not an RPC — a new `sync_state` table holds the cursor, and rows with a pending local edit are skipped entirely, not merged

- **Date:** 2026-09-14
- **Decision:** `src/lib/syncPull.ts#pullChanges()` reads every row from `projects`/`inspections`/`answers` where `server_updated_at` is newer than a locally-stored cursor, oldest first, via plain `supabase.from(table).select("*").gt("server_updated_at", cursor)` — three ordinary reads, not a Postgres function. Each pulled row is either upserted into local SQLite (a new `applyPulledX` function per repository, D-019's `setXSyncStatus` sibling — no transaction, no outbox write, stamps `syncStatus: "synced"`) or, if the same entity has a pending outbox row, left completely untouched. The cursor itself lives in a new one-row-per-key table, `sync_state` (`src/db/schema.ts`, migration `drizzle/0002_glossy_smiling_tiger.sql`), storing the exact ISO-8601 string Postgres returns for `server_updated_at` — never converted to or from this project's usual epoch-ms shape, so no timezone or precision bug can creep in at the one boundary this entire phase depends on.
- **Why a table and not an RPC, when push (D-019) specifically chose the opposite:** push needed one function because "check the idempotency key, then apply the change, then record the key" has to happen atomically — three steps, one all-or-nothing unit. Pull has no equivalent atomicity requirement: each table's read is independent, RLS already restricts every row to the signed-in user, and there's nothing to protect against by wrapping three unrelated `SELECT`s in a single database function.
- **Why a new table for the cursor and not a column on some existing row:** the cursor isn't data about any project or inspection — it's data about the sync process itself, the same reasoning `outbox` already used to justify not sharing `commonColumns()` with every entity table (D-005). Storing it as a plain key/value row keeps it just as separate.
- **The merge rule that matters most:** a pulled row is applied only when `listOutboxForEntity(row.id)` comes back empty. A row with its own pending outbox entry is left exactly as it is — not overwritten with the incoming server version, not merged field-by-field, nothing. This is deliberately unsophisticated: the plan's own Day 4 scope says "never overwrite a local row with unsynced pending changes; leave it for conflict handling," and Day 5 is where an actual policy for that case gets built. Doing anything cleverer here would mean building (and then probably rebuilding differently) a conflict resolution rule one day early.
- **The resurrection bug (plan Section 2.7) — live-verified, not just reasoned about:** a throwaway script walked through the textbook failure: insert an inspection, delete it (Device A style), then push a plain field-only _update_ for that same row with a fresh idempotency key (Device B's stale edit, made before B ever saw the delete — exactly the payload shape `updateInspection` actually produces, which never carries a `deletedAt` key). Real, observed result: `deleted_at` stayed set throughout — B's update changed its own field (`title`) but never touched, let alone cleared, the tombstone — and a pull query run immediately after still saw the row with `deleted_at` populated, exactly as a tombstone should look to a fresh puller. This was **already true because of how D-019's `sync_push` update branch was written** (it only ever writes `deleted_at` when the payload explicitly carries that key) — Day 4 didn't need to add anything to prevent this specific failure, only to confirm, with a real run against the real backend, that it actually holds.
- **An honest, minor nuance this surfaced, not hidden:** that same script showed a stale non-delete update _does_ still apply its own fields to an already-deleted row (the title changed even though the row stayed deleted). The row remains invisible either way — every screen already filters `deletedAt IS NULL` — so nothing user-visible is wrong, but it's not free of any effect either. Whether a should-be-inert edit to a dead row deserves special handling (skip it entirely once a row is known deleted) is exactly the kind of question Day 5's conflict policy (rule R4, "delete vs edit") is scoped to answer properly — noted here rather than patched ad hoc.
- **What's live-verified versus what isn't:** the actual PostgREST query shape, the tombstone surviving a stale concurrent update, and a pull query correctly returning a deleted row's `deleted_at` were all run for real against the live backend. What hasn't been exercised end to end, for the same D-010 reason as every earlier Day 2–4 client-side gap: the full `pullChanges()` merge loop actually writing to local SQLite, and the "skip if pending" branch actually leaving a real local row alone — this web preview's real SQLite never opens, so there is no real local row for either code path to touch.
- **Rejected:** attempting any field-level merge or "pick the newer field" logic for a row with a pending local edit — rejected for now, not because it's wrong in principle, but because building it correctly needs the server-timestamp comparison and worked examples Day 5 is specifically scoped to define (plan Section 5). A same-day-guessed version would very likely need to be rebuilt tomorrow anyway.

### D-022: Conflicts are detected and resolved during PULL, not via a push-time 409 — because there is no `baseVersion` to check against

- **Date:** 2026-09-14
- **Decision:** the plan's Section 4.1 protocol assumes push carries a `baseVersion` (what the client last saw) and the server returns `409` when it doesn't match, at which point the client "runs the Section 5 policy." This project's `sync_push` (D-019) does neither — it has no concept of a base version, and never returns 409. Conflict detection instead happens in `src/lib/syncPull.ts`, the moment a pulled row is found to have a pending local outbox entry for the same entity: that's the one condition that structurally means "both sides changed since this device last agreed with the server," the same condition Section 3.5.1 defines detection by, just discovered from the other direction.
- **Why not add `baseVersion` properly instead:** doing this the way the plan literally describes would mean mirroring `server_updated_at` into a local column on every entity table (a schema change), having every push include it, and teaching `sync_push` to compare it and reject with a structured conflict payload — a real, larger feature, and one this project's actual backend shape (Supabase + RLS + a plain upsert-style RPC) doesn't need in order to get the same real guarantee. Detecting at pull time, using infrastructure (the outbox, `listOutboxForEntity`) that Phase 1 already built for an unrelated reason, reaches the identical decision point — "local and server both changed" — without inventing a parallel versioning system.
- **The resolution engine (`src/lib/conflict.ts`) is one pure function, `resolveConflict`, shared by all three synced entity types** (projects, inspections, answers) — no I/O, just data in, a decision out, parameterized by which fields the caller should even consider (`ignoreFields`) so the same function doesn't need to know that inspections have a `projectId` and answers don't.
- **R3 ("newer server timestamp wins"), reinterpreted for an edit that hasn't been server-timestamped yet:** the plan's R3 assumes both versions already have a real server timestamp to compare. A pending local edit doesn't — it's about to get one, on the very next push, which happens moments after this pull (`src/lib/sync.ts#runSync`: push, then pull — so the push that finally delivers this edit is the _next_ sync's, immediately following). Once it does, its server timestamp will be newer than the one already sitting in the row just pulled (which is, by definition, from before this moment). So for a same-field disagreement that isn't within the R7 window, keeping the local value and letting it push is equivalent to letting the genuinely newer edit win — without ever comparing an un-synced device clock against the server's, which D-017 already rules out.
- **R4 ("delete vs edit: newer wins, delete usually"), made unconditional rather than clock-compared:** an incoming tombstone for an entity with a pending local edit always wins here — never compared against the local edit's own (unsynced, device-clock) timestamp. The same D-017 reasoning applies: there is no trustworthy way to know a not-yet-server-confirmed local edit is "newer" than an already-server-confirmed delete. Treating the confirmed delete as authoritative, unconditionally, is the defensible default the plan's own "usually" leaves room for.
- **A real bug, caught by actually running the plan's own worked examples through the real function, not by re-reading the code:** the first version's R2 branch was written `if (!localEmpty || serverEmpty)` — a boolean-logic slip (OR where AND was meant) that made it `true` whenever local simply had _any_ real value, completely swallowing the R7 "flag for a person" branch beneath it. Every same-field, both-non-empty case silently fell through to "keep local," including ones inside the 60-second window Example 3 (the "Structural damage, urgent" scenario) exists specifically to protect. Caught by writing the plan's Section 5.2 examples as executable checks against the real `resolveConflict` — Node 24's native TypeScript support made this possible without a build step — and watching Example 3 fail. Fixed by splitting the condition into its three actual cases (`localEmpty && !serverEmpty`, `!localEmpty && serverEmpty`, `localEmpty && serverEmpty`) instead of one collapsed, wrong one.
- **A second, deeper bug the same test run surfaced — a genuine false-positive, not a typo:** even after the R2 fix, a field only THIS device had ever touched could still get incorrectly flagged for manual resolution, purely because the server's (stale, unrelated) value for that field trivially differs from local's brand-new edit — nothing to do with anyone actually racing it. Fixed by adding one more check: if the pulled row's `server_updated_at` predates this device's own local edit, the server genuinely hasn't heard about that edit yet — every "difference" against it is expected, and none of it is a real conflict, regardless of the 60-second window.
- **An honest, remaining limitation, not silently smoothed over:** the fix above only catches the common case (server hasn't changed _at all_ since before the local edit). It does not fully solve per-field attribution — if a genuinely different device changes a _different_ field on the same row, within the 60-second window, this device's own untouched-by-anyone-else field can still occasionally get flagged for manual review it didn't need, because the "close in time" check operates at the row level (one `server_updated_at` for the whole row), not per field. Precisely fixing this needs either per-field version tracking or a stored last-known-server snapshot per row — real infrastructure beyond what Day 5 is scoped to build. The failure direction is the safe one: an occasional unnecessary question to a person, never a silently discarded edit.
- **Live-verified, not assumed:** all seven of the plan's own worked scenarios — different-fields merge (Example 1), the stale-pull false positive, R2's empty-side rule, same-field-not-close-in-time, same-field-close-in-time (Example 3, word for word), an incoming tombstone beating a pending edit, and a local pending delete proceeding untouched — were run as real assertions against the actual `resolveConflict` function, not a re-implementation or a hand-trace. The R2 bug and the false-positive bug were both caught this way, before either shipped.
- **What's still unverified, for the familiar D-010 reason:** everything downstream of `resolveConflict`'s decision — `syncPull.ts` actually writing a field merge to local SQLite, recording a `conflicts` row, and the Settings screen's resolution UI calling `resolveConflictChoice` to push a person's choice onward as a normal edit — is typecheck/lint-clean and wired correctly by inspection, but this web preview's real SQLite never opens, so none of it has run against a real local row. The two test cases the plan itself says prove Phase 3 worked (TC-25, TC-29) need two real phones regardless of anything built here.
- **Rejected:** trying to also fix the row-level "close in time" imprecision today by adding per-field snapshot tracking — rejected as genuine scope creep for one day, documented as a known limitation instead of quietly shipped as if it weren't there.

### D-023: Attachment upload is three separate operations treated as one atomic-per-attempt sequence — row push, file upload, then a remote_url follow-up push

- **Date:** 2026-09-14/15
- **Decision:** `src/lib/attachmentUpload.ts#pushAndUploadAttachment` replaces the plain `pushOutboxEntry` for `entityType === "attachment"` insert entries (wired in `src/lib/syncEngine.ts#pushOne`). It does, in order: (1) push the attachment row via `sync_push`'s new `attachment` branch (`supabase/migrations/20260914000001_sync_push_attachments.sql`) with `remote_url = null` — truthfully, since the file hasn't uploaded yet; (2) read the local file's bytes (`expo-file-system`'s `File.bytes()`) and upload them to a private Supabase Storage bucket (`supabase/migrations/20260914000002_attachment_storage.sql`); (3) push a second, small `sync_push` update setting `remote_url` to the object's storage path. The outbox entry is only ever deleted (`src/lib/syncEngine.ts#pushOne`) after all three steps return success — so a failure or an app kill at any point leaves it exactly where it was, untouched, and the next drain redoes the whole thing.
- **Why three steps can safely be "redone from scratch" rather than needing to resume from wherever they stopped (plan Section 3.6.2's resumability requirement):** every step is independently idempotent. Step 1 is `on conflict (id) do nothing` — a repeat is a no-op, same as every other entity's insert. Step 2 uploads with `upsert: true` — re-sending identical bytes to the same path overwrites cleanly, never fails or duplicates. Step 3 sets `remote_url` to the value it would already be if a previous attempt got that far — repeating it changes nothing. Because none of the three steps has a side effect that compounds on retry, "start over" and "resume" are behaviorally identical here, and "start over" is far simpler to reason about and verify.
- **Why the object path IS the ownership check (`{owner_id}/{attachmentId}{ext}`), not a Storage-native `owner_id` column:** `storage.objects` has no such column for this project's use — Supabase Storage's own convention for row-level ownership is to encode it in the path and read it back with `storage.foldername(name)[1]`, mirroring the `auth.uid() = owner_id` shape every table's RLS already uses (D-017), just sourced from the path instead of a column.
- **Why `remote_url` stores a raw object PATH, not a URL:** the bucket is deliberately private (`public: false`). Storing a public URL would mean either making the bucket public (any inspection photo readable by anyone with the link, forever — wrong for private field-inspection photography) or storing a signed URL, which silently expires and stops working. A path is the one representation that's both private and doesn't rot; viewing a photo later means calling `supabase.storage.from('attachments').createSignedUrl(path, ttl)` on demand, short-lived, exactly when a screen actually needs to render the image — not built yet, since no screen displays a synced (as opposed to locally-cached) attachment image today; see docs/SYNC.md's status table for what that leaves open.
- **Why step 3 uses a brand-new random idempotency key on every attempt, rather than reusing one derived from the outbox entry's id:** the entry's own `id` is already spent as step 1's key (it names "insert this specific row," a real, non-repeatable side effect worth deduplicating strictly). Step 3's update has no such side effect to protect — setting `remote_url` to the same value twice is a true no-op regardless of which idempotency key names the attempt. The honest cost: a retried follow-up leaves more than one row behind in `sync_idempotency_keys` for the same attachment, one per attempt. Accepted rather than engineered around, because that table is a dedup LOG (Day 2, D-019), not user-facing data — nothing reads "how many keys does this attachment have," and the field-level correctness that idempotency exists to protect isn't affected either way.
- **What a delete does NOT do:** `pushAndUploadAttachment` only special-cases `operation === "insert"` — a pending delete (a tombstone, `{id, deletedAt}`) has no file to upload, so it goes through the same plain `pushOutboxEntry` every other entity's delete already uses. Deliberately not built: deleting the underlying Storage object when an attachment is soft-deleted. The row is gone from every list a user sees either way; the orphaned file sitting in Storage is a real but low-stakes cost (storage space, not a privacy leak — RLS on the bucket still means only its owner could ever read it), and cleaning it up is straightforward future work, not attempted today to keep Day 6 inside its timebox.
- **Verification status, precisely:** the two SQL migrations were applied to the live Supabase project by the user (no service_role key or linked CLI project exists in this sandbox — by design, D-018's boundary extended: this project never puts write/DDL credentials anywhere Claude Code can reach them — so this step could only happen outside this tool). A throwaway verification script (same pattern as every prior day) then confirmed live: the attachment insert/update branches work, idempotent replay returns `duplicate: true`, and a second, independently-signed-in client successfully reads the completed row back. The actual device-side flow — `expo-file-system` reading real photo bytes and uploading them — remains unverifiable in this environment regardless (no physical device, D-010); this is a step beyond every previous day's story, not a repeat of it, since Days 1-5 only ever needed to prove *server* behavior, never a real device's filesystem.

### D-024: Background execution — only what's realistically buildable and shippable inside Expo's MANAGED workflow, with a deliberate, documented scope cut for the rest

- **Date:** 2026-09-15
- **Decision:** `src/lib/backgroundSync.ts` registers `runSync()` as a periodic task via `expo-task-manager` + `expo-background-fetch` — a genuine OS-owned timer that may wake the app for a few seconds occasionally (a floor of ~15 minutes on the request, never a guarantee the OS honors that often). Registered once, from `src/app/_layout.tsx`, the moment a session exists, mirroring `startAutoSync`'s gating — but reached only through a *dynamic* `import()`, guarded by `Platform.OS !== "web"`, never a static import. `expo-task-manager`'s `defineTask` runs its side effect at module load time, and this project does not assume that's safe to even *load* on web just because most Expo native modules degrade gracefully there — `expo-secure-store` (D-018) is the exact, hard-won counterexample: it didn't degrade, it crashed the whole app to a blank screen the moment it was touched on web. A dynamic import that's simply never called on web is a stronger guarantee than a runtime `if` inside a statically-imported module, because the module's own top-level code then genuinely never runs there at all.
- **What this deliberately does NOT attempt, and why — the plan itself grants explicit permission to cut this** ("If you fall behind, cut in this order: 1. Background execution... A well-documented understanding of why background execution is unreliable is worth more in an interview than a half-working implementation"):
  - A real background `URLSession` on iOS that keeps an upload genuinely running after the app is suspended, past the few seconds a background-fetch wake-up gets. That needs a native iOS extension/target and `NSURLSessionDelegate` wiring — outside Expo's *managed* workflow entirely (this project is not a bare/ejected workflow, and building one needs a Mac, Xcode, and a real device this sandbox doesn't have).
  - A real Android foreground service (a persistent, user-visible notification while an upload runs) — same reasoning: a custom native Android module `expo-background-fetch` doesn't provide.
  - Any actual execution/scheduling verification: background fetch fundamentally only runs on a real, physical, signed dev-build install — not Expo Go, and there's no physical device available in this sandbox (D-010, extended). The registration code is typecheck/lint-clean and its task body calls the exact same `runSync()` already live-verified server-side (Days 2-5); the registration and periodic scheduling itself has not executed once, by anyone, as of this commit.
- **Rejected: ejecting to a bare/custom-native workflow to build the real thing.** Would genuinely solve the "unreliable" problem this decision is naming — but converts the whole project from managed Expo (what every other Phase 1-3 decision assumes) into a different kind of project, unbuildable and unverifiable in this environment regardless, and outside what one day is scoped to absorb. A well-reasoned "here's exactly what's missing and why" is the plan's own explicitly preferred outcome over attempting this and shipping something broken or untestable either way.
- **What IS true and shippable today:** even without background execution working reliably, sync in this app is never actually stuck waiting on it — `startAutoSync` (Day 3) already covers "reconnect" and "app returns to foreground," and the manual "Sync Now" button always works. Background fetch is a nice-to-have on top of guarantees that already exist, not something correctness depends on — which is precisely why it was the right piece to timebox rather than the wrong one to skip pull, push, or conflict resolution for.

### D-025: Attachments needed to be pulled too, and `local_uri` needed to become nullable — a real gap found while preparing Day 7's test pass, not part of the original Day 6 plan

- **Date:** 2026-09-15
- **The gap:** `src/lib/syncPull.ts` (Day 4) only ever pulled `projects`, `inspections` and `answers` — written before attachments were push-able at all (Day 2's placeholder rejection, D-019). Day 6 made attachments push-able but never revisited pull. Left as-is, TC-30 ("both devices add photos offline to the same inspection, both sync → both sets present," plan Section 6.2.5, testing rule R6) would have silently failed: device B would never learn device A's photos exist at all, regardless of anything Day 6 built. Found by checking the plan's own R6 rule against the actual pull code while preparing Day 7's test pass — not by running TC-30 itself (still needs two real clients either way).
- **Decision:** `src/lib/syncPull.ts` now also pulls `attachments`, reusing the exact same generic `pullTable`/`EntityHandlers` machinery the other three entities already use — no new pull mechanism needed. `src/repositories/attachments.ts` gained `getAttachmentById` and `applyPulledAttachment` (the `getLocalRow`/`applyFullRow` half of an `EntityHandlers` entry, same shape as the other three repositories already have) plus `applyServerFieldMerge` for shape-parity with the shared type (see below for why it's realistically dead code here).
- **Why R6 ("never conflict, unique IDs, keep both") holds structurally, not just by policy:** an attachment's `id` is generated once, client-side, by whichever device captured it. A row with a pending LOCAL outbox entry for that exact id can only ever exist on that SAME device — by the time any OTHER device could pull that row at all, the originating device's own push has already succeeded and its outbox entry is already gone (`syncEngine.ts#pushOne`'s "only delete on `ok:true`" rule). So `pullTable`'s conflict-detection branch (`pendingEntries.length > 0`) is never actually reachable for an attachment — every attachment pull takes the plain-upsert path, which is exactly what "keep both, no conflict" means when there's nothing to actually compare. `resolveConflict`/`applyServerFieldMerge` were still wired up identically to the other three entities, for one reason: uniformity makes `pullTable` generic over all four entities with zero special-casing, which is a real, verifiable property (the same function, unmodified, produces correct behavior for both "can genuinely conflict" and "structurally can't" entities) rather than an assumption resting on attachments being handled by different code no one has to keep in sync with the other three.
- **A second, harder problem this surfaced: whose filesystem does `local_uri` describe?** Every other synced column has one true, shared value the server holds. `local_uri` doesn't — it's a path on ONE specific device's filesystem, and the server only stores it because it rode along in the same insert payload for convenience (`supabase/migrations/20260914000001_sync_push_attachments.sql`'s own comment already called this out as "purely informational"). Blindly upserting a pulled row's `local_uri` onto a different device would write a path that looks real but points at nothing that device can read — not a crash (nothing in this app ever opens a file at a path it didn't verify with `file.exists` first — see D-023), but a real, misleading piece of local state.
- **The fix, and why it needed the column to become nullable:** `attachments.local_uri` (`src/db/schema.ts`, migration `drizzle/0004_fancy_edwin_jarvis.sql`) dropped its `NOT NULL` constraint — a device genuinely may know an attachment exists without having its bytes on disk at all. `applyPulledAttachment` never writes a server-sourced `local_uri` under any circumstance: a genuinely-new-to-this-device row inserts with `local_uri: null` ("no local file exists here, and that's an honest statement, not a bug"); a row this device already has (almost always its own attachment, echoed back by a later pull once its own push has already succeeded) keeps whatever `local_uri` it already had, by excluding that one column from the `onConflictDoUpdate` SET clause entirely — Postgres/SQLite upsert semantics only touch the columns actually listed, so an untouched column survives a repeat upsert unchanged. This was the one place in the whole sync system where "just upsert everything the server sent" (every other `applyPulledX` function's whole strategy) would have been actively wrong, not just unnecessary.
- **UI consequence, kept intentionally minimal:** `FormRenderer.tsx`'s attachment list already only ever rendered `a.localUri` as plain text (Phase 2 never built real image rendering — no `<Image>` component reads these files today). The Day 7 change is the smallest honest fix: when `localUri` is null, show `(synced from another device: {remoteUrl})` instead of blank text, so a photo that exists but isn't locally downloadable is at least visibly accounted for. Deliberately NOT built: actually fetching a signed URL and displaying real image bytes for a non-originating device's photo — real new scope (a network fetch, a cache decision, a loading state), not a continuation of anything already in flight, and out of what Day 7's 3-hour "test, document, submit" budget is for (plan Section 3.7). Recorded here as a known, explicit gap rather than silently left for someone to discover.
- **Rejected: leaving `local_uri` required and inventing a placeholder string (e.g. `""` or `"remote-only"`) for a pulled row instead of `null`.** Would have avoided a schema migration, but trades a real, honest signal ("this column has no meaningful value") for a magic string every reader of this column would need to know to special-case — exactly the kind of implicit convention this project's whole documentation discipline exists to avoid. `null` is what TypeScript, Drizzle, and SQL all already have a first-class way to check for; a sentinel string is a fact only a comment can convey.
- **Verification status:** typecheck/lint-clean; the migration is a standard Drizzle-generated SQLite table rebuild (drop `NOT NULL`), the same shape as every other schema change in this project. Live-verified against the real Supabase project, once the D-023 dependency (the two Day 6 SQL migrations) was applied there: the same throwaway verification script this project has used since Day 1 proved R6/TC-30 directly — pushed an attachment as "client A," then read it back via a second client sharing the same account (the plan's "👥 two clients" — this app has no cross-account sharing model, RLS is strictly per-owner, D-017), confirming it came back with the right fields and a `remote_url` filled in by the follow-up push.

### D-026: PDF report generation (Day 1) — HTML-to-PDF, and three deliberate deviations from the plan as written

- **Date:** 2026-09-16
- **HTML-to-PDF over direct drawing:** `expo-print`'s `printToFileAsync({ html })` renders a plain HTML string using the OS's own print engine, instead of a PDF-drawing library that requires positioning every element by coordinate. Page breaks, text wrapping, and image scaling all come for free from CSS (`page-break-inside: avoid`) instead of being this project's problem to solve by hand. The real constraint this trades in for: `expo-print`'s renderer is not a browser — no JS execution, no external stylesheets, no network-fetched fonts — so `src/lib/reportHtml.ts` inlines every style in one `<style>` block and every image as a base64 `data:` URI (`src/lib/reportImages.ts`), never a `<link>` or a `file://` `src`.
- **No `rating` field type.** The plan's Section 4.2 formatting table includes a rating-to-"4/5" rule, but grepping the whole codebase turns up no `rating` field type anywhere — `FormRenderer.tsx`'s field-type `switch` has never had a case for one, and neither seeded template (`src/db/templateDefs.ts`) uses it. Adding a new field type as part of a PDF-generation day would be exactly the feature creep Phase 4's own freeze rule (0.2.1/1.3.2) warns against — `src/lib/report.ts`'s formatter simply has no `rating` case. If one is ever added to the template format, its display formatting slots in as a one-line addition then, not invented speculatively now.
- **No per-photo captions — the field's label is used for its photo group instead.** The plan wants a "photo grid with captions." There is no caption column anywhere in `attachments` (`src/db/schema.ts`), and nothing in the app has ever captured free-text per-photo captions — building that would be a real new feature (a text input, a save path, a migration), not a Day 1 reporting task. `src/lib/report.ts` groups a section's photo attachments by `fieldKey` and uses the field's own `label` (e.g. "Damage Photos") as that group's single caption in the report, which is genuine, already-captured data rather than an invented one.
- **No static map image.** Plan Section 4.1 says "static map if available." A static map means fetching map tiles over the network, which directly contradicts Section 4.3's own explicit constraint: "must generate fully offline, no network at any point." Rather than silently pick one side of that contradiction (either breaking offline generation, or quietly dropping "if available" language that implied it should exist), the report's Location section shows only the raw coordinates and accuracy from a `gps`-typed answer (when the template has one) and omits the map image entirely — documented here rather than left for someone to notice the plan wasn't followed literally.
- **No persisted photo thumbnail, so full-size images are inlined, capped at `MAX_INLINE_IMAGES = 20`.** `takePhotoAndCompress` (`src/lib/media.ts`, Phase 2) does generate a 200px thumbnail alongside the 1600px full image, but the thumbnail path is never written to the `attachments` table — it only exists transiently in `FormRenderer`'s in-memory state right after a fresh capture (`thumbLocalUri`, attached client-side, never persisted). A report built from the database days or weeks later has no thumbnail to reach for, only `localUri` (the full image). Plan Section 2.2's own memory-exhaustion warning ("thirty full-size images inlined at once will exhaust memory... cap the images per report and note the limit") is honored by capping at 20 total (photos + signature) and stating in the report itself when photos were truncated, rather than silently dropping them past the cap.
- **No existing base64-file-read utility existed anywhere in this codebase** before this day — every prior use of `expo-file-system`'s `File` API either wrote base64 (`SignaturePad`'s PNG write) or read raw bytes for a network upload (`attachmentUpload.ts`'s `file.bytes()`, Day 6). `File` itself has no built-in base64 reader (checked the installed package's own `.d.ts`). `src/lib/reportImages.ts#localUriToDataUrl` reads a file's raw bytes and hand-encodes them to base64 (a small, standard RFC 4648 encoder — not worth a new dependency for), returning `null` rather than throwing if a file is missing or unreadable, so one bad photo can't fail an entire report.
- **Verification status, precisely:** `npm run typecheck` and `npm run lint` are both clean. The web preview boots with no console errors, confirming the new code (`src/lib/report.ts`, `reportImages.ts`, `reportHtml.ts`, and the new button in `src/app/inspections/[id].tsx`) doesn't break Metro bundling — but that is a smoke test only, and `expo-print`'s actual rendering is a native module that does not function in the web preview at all. Generating and visually checking a real PDF (plan's own "▶ SEE IT RUN" for this day: a real completed inspection, and a synthetic 40-photo inspection to check pagination) needs either a physical Android/iOS device or a working Android emulator — this sandbox has neither: the same Windows Hypervisor Platform / admin-rights wall documented while setting up Phase 3's device testing blocks the emulator here too, and there is no physical device available. This is **built but not live-verified**, named honestly rather than reported as done.

## D-034 — `select` fields were free-text boxes; a phone keyboard silently broke `visibleIf`

**Found on the A51, not before.** `FormRenderer.tsx`'s `select` case rendered a plain `Input` with the option labels as placeholder text. ## D-035 — Photo "long edge 1600" was actually width-only; measured on the A51

**Measured on a real phone (first time this was ever possible).** Two photos taken in the app on a Samsung A51 were saved at 300,591 and 178,847 bytes; both decoded (JPEG header) to **1600 × 2844 px**. `src/lib/media.ts` commented "long edge 1600" but called `manipulateAsync` with `resize: { width: 1600 }`, so a portrait photo keeps its aspect ratio and ends up with a 2844 px long edge (~4.5 MP). Compression is a fixed quality (0.7), not a size target, so file size varies with scene detail — the plan's "under 300 KB" was never guaranteed by construction, only true for lucky scenes. 300,591 B is 300.6 kB (decimal) / 293.5 KiB: over by the 1000-byte definition, under by the 1024 one — borderline either way.

**Fix.** Resize the long edge: `{ height: 1600 }` for portrait (from the camera asset's own width/height), `{ width: 1600 }` otherwise. Expected result ~900 × 1600 (~1.4 MP, roughly a third of the pixels). **Not yet re-measured after the fix** — a new portrait photo is needed; result to be added to `TEST-RESULTS-DEVICE.md`.

**Still not size-targeted.** If a hard 300 KB cap matters, the honest options are lowering quality for large results or a second pass; not done — measure first (the plan's own rule).

## D-038 — No inspection created in the app could ever sync (template ids), plus a fake-photo fallback

**Found by the airplane-mode test on the A51.** Reading the phone's outbox after reconnecting: the queued `inspection` insert had failed with `invalid input syntax for type uuid: "roof-inspection-v1"`, and its child `answer`/`attachment` inserts failed with `..._inspection_id_fkey` (the parent never arrived).

**Root cause (two gaps that compound).**
1. `seed.ts` used the template JSON's human slug (`"roof-inspection-v1"`) as the template row's database primary key (`id: t.id ?? newId()`), contradicting the rule already written in `CLAUDE.md` ("a template row's database `id` (UUID) is a different value from the JSON payload's own `id` slug"). 2. No migration ever inserted a template row on the server, so even a valid UUID would have failed the foreign key. `syncPull.ts` doesn't pull templates either — they were assumed to exist on both sides.

**Why nothing caught it for two phases.** Phase 3's live checks were scripts pushing rows with `template_id: null`, and no device ever ran the real create → push path end to end. "Phase 3 live-verified" was true for the sync mechanics (idempotency, conflicts, RLS) and false for "an inspection made in the app reaches the server". This is a correction to how that claim should be read.

**Fix.** `TemplateDef` gains `dbId` — a fixed UUID per template, the same on every device; seeding and the web mock use it as the row id (the slug stays inside the JSON). New migration `supabase/migrations/20260920000001_seed_templates.sql` (generated from `templateDefs.ts`, idempotent `on conflict do nothing`) inserts the same rows on the server. **It must be run once by the project owner in the Supabase SQL editor** (clients have SELECT-only on `templates`, deliberately). `templateDefs.test.ts` (+5 tests, 27 total) fails if a `dbId` isn't a UUID / isn't unique / is the slug, or if the migration file stops matching the app's ids and schema JSON.

**Consequence.** Existing local databases hold the old slug ids and stay unsyncable — reseed (dev data) or, for real users, a one-off migration. There are no real users.

**Also fixed (same test, same anti-pattern as D-036/D-037).** `FormRenderer.tsx` "Add photo" created a fake attachment (`file:///placeholder.jpg`, 12,345 bytes, 800×600) whenever the result was `null` (the person **cancelled** the camera) or an error. Now: cancel does nothing; an error alerts and saves nothing. The camera itself failing to open offline is likely a dev-build artifact (modules are lazy-imported and fetched from Metro, which is unreachable in airplane mode) — unconfirmed; a production build bundles everything.

**Not yet verified:** that an inspection now syncs. Needs the migration applied + a reseed + a fresh inspection; see `TEST-RESULTS-DEVICE.md`.

## D-040 — Finishing the app without the phone (part 1: templates actually exist; a third template)

**A fresh install had no templates.** The only code that put templates on the phone was the dev "Reset & Reseed" button (which also wipes everything and makes 500 fake inspections). Found by reading who writes to the `templates` table, while planning what "complete" still needs.

**Fix.** `ensureBuiltInTemplates()` (`src/repositories/templates.ts`) runs at startup, after migrations and before the app opens (`MigrationGate` in `_layout.tsx` waits for it). Failure is non-fatal and reported. 5 integration tests against a real in-memory SQLite (fresh DB, idempotent, no outbox, upgrade, no-downgrade); mutation-checked — removing the version guard fails 2. **Alternatives rejected:** pulling templates from the server (a second moving part and a network dependency for something that ships inside the app); seeding on first launch only (breaks when a template version is bumped).

## D-041 — Finishing the app without the phone (part 2): a sync data-loss bug, number input, `date`, more `visibleIf`

**1. Answers could silently never reach the server (found by reading, reproduced by a test).** `saveAnswer` keeps the outbox compact by replacing a field's pending entry on each autosave — but it deleted **every** entry for that answer, including a still-unsent **insert**, and queued an **update** instead. `sync_push`'s update branch is `update … where id = …`: for a row the server never received it matches nothing and reports success. So any answer saved twice before a sync (any text typed over a few seconds, any offline edit-then-edit) stayed on the phone forever and never reached the server. Phase 3's live checks pushed answers by script, never through `saveAnswer`, so nothing saw it. **Fix:** if an unsent insert exists it stays an insert and its payload is replaced with the latest full row; otherwise the old replace-pending-update behaviour. `answers.integration.test.ts` (5 tests, real in-memory SQLite) failed 2/5 on the old code (exactly the two "save twice before sync" cases) and passes 5/5 now. Other repositories don't do this — projects/inspections append separate entries. **Not yet confirmed end to end on a device.** Alternative rejected: making the server's update an upsert — it would hide the missing-insert problem instead of removing it, and an update payload doesn't carry the columns an insert needs.

**2. Number fields couldn't take decimals or be cleared.** The box stored `Number(text)` on every keystroke: "3." became 3 (the dot vanished, so 3.3 V was untypeable) and a blank box became 0. New `NumberField` shows the person's own draft while editing (no effect/sync logic — the linter rightly rejected an earlier effect-based version) and stores only what `parseNumberInput` (`src/lib/numberInput.ts`, 5 tests) accepts; blank now stores "no answer" (all three answer columns null). Not verified on a device.

**3. `date` field type** completes the plan's ten. Stored as the **text** `YYYY-MM-DD`, not an epoch-ms timestamp: a calendar date has no time zone, and converting would shift it a day for someone elsewhere (the earlier `report.ts` branch that expected epoch-ms was never reachable — no field produced one). Entry is typed with automatic hyphens (`formatDateInput`), validated as a real calendar date (`isValidIsoDate` rejects 2026-02-30 and non-leap 02-29), shown in reports as "21 Sep 2026" (month as a word, so it can't be misread as day/month). **Rejected: a native date picker** — needs a new native module, hence a new build, and can't be tested without the phone. Helpers: 13 unit tests; validator: 2 more. "Site Safety Walk" gains a `walk_date` field (its server migration had never been applied, so it was regenerated; the zero-code proof stays commit 05c254c).

**4. `visibleIf` gains `equals` and `notEmpty`** (the plan's Section 4.4 named all three). `in` is unchanged; several operators on one rule must all hold; `equals` is strict (`0`, `1` for a ticked boolean, and the string `"1"` differ); `notEmpty` treats `""`, `null`, `[]` and missing as empty but `0` as an answer. 12 tests, one mutation-checked. Freeze note: items 2–4 are engine additions made at the user's request ("make the app complete"); item 1 is a bug fix.

**Status:** all built and unit-tested (80 tests); none of it run on a device. The migration `20260920000002_seed_safety_walk_template.sql` (regenerated with `walk_date`) still needs to be run by the project owner.

## D-042 — No signal is not a failure of the data (sync retry budget) + the first sync-engine tests

**The problem (found by reading the engine, then confirmed by a failing test).** `drainOutbox` treated every failed push alike: one attempt spent, exponential backoff, dead-lettered after `MAX_ATTEMPTS` (8). And `pushRowOnly` marked every error without a Postgres code as "retryable". Sync is also triggered on every app-foreground event — even with no connection. So an inspector with no signal who kept opening the app burned all 8 attempts in roughly four minutes of foreground use (1+2+4+…+128 s of backoff) and the rows were dead-lettered, needing a manual "Retry Failed". For an app whose whole premise is working without coverage, that is backwards. A second, narrower instance: `attachmentUpload` called `supabase.auth.getUser()` — a **network** call — and returned `retryable: false, "Not signed in"` if it failed, so a signal dropping between the row push and that line dead-lettered a good photo permanently.

**The fix.** (1) `PushResult` gains `unreachable`: a failed RPC whose error has **no code** never got an answer (every server-produced error carries a Postgres SQLSTATE or PostgREST `PGRST…` code; a transport failure has an empty one). Storage upload errors use the same idea (no HTTP status). (2) `pushOne`, on an unreachable failure, puts the row back exactly as it was — status `pending`, **no attempt spent, no error recorded**. (3) `drainOutbox` stops at the first unreachable failure (`result.offline = true`): everything after it would fail the same way, and this also stops it hammering. (4) Photo upload reads the user id from the stored session (`getSession()`, no network) instead of `getUser()`.
**Consequence to know:** an unreachable row is due immediately, so it's retried on the next trigger (reconnect / foreground) rather than after a backoff; that's one request per trigger, not a loop. Backoff and dead-lettering still apply to genuine server rejections, unchanged.
**Alternatives rejected:** raising `MAX_ATTEMPTS` (just delays the same failure); a separate "offline" counter with its own cap (more state for the same effect); checking `NetInfo` before syncing (racy and doesn't cover "connected but no route").

**Tests.** `syncEngine.integration.test.ts` — 10 tests, the engine's first, real repositories + real in-memory SQLite with only the network call faked: success, parents-before-children ordering, retryable failure (1 attempt, backoff, still pending), permanent failure (dead-lettered at once), dead-letter exactly at `MAX_ATTEMPTS`, "Retry Failed" delivers, and the four D-042 behaviours (no attempt spent; 24 offline drains never dead-letter; drain stops after the first unreachable; entries queued offline are delivered exactly once when the signal returns). The four new ones failed before the change; removing the early stop fails 1, removing the no-attempt branch fails 4.
**Also verified:** `npx expo export --platform android` builds a production JS bundle cleanly (exit 0) — the dev server can hide release-only breakage.
**Not verified:** any of this against real supabase-js network errors on a device (the "empty code" assumption comes from supabase-js/postgrest-js behaviour and the error shapes seen in this project's own outbox; a phone test in airplane mode is the check), and the attachment path's status detection.
